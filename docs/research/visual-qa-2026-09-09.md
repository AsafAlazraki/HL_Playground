> **The question.** The owner has said repeatedly that the app looks bad. Two passes have
> now changed it — the prose pass and the display tier (`94e0694`, *"The app had a 2.97x
> scale where its own spec asks for 7x"*) — and nobody has checked the result. This is the
> check. Numbers, not opinions.
>

> **7.53×** at 1280, which is exactly what `DESIGN_CONTRACT.md:192` predicted. Every other
> screen measures **2.44× to 3.96×** there, and the home stage — the screen the 2.97× figure

> One real contrast failure was found, in **21 places** across the register, on a screen

**Contrast uses `check-contrast.mjs`'s ruler unchanged** — parse `color(srgb …)` as well as
`rgb()`, composite the **full** ancestor chain, composite translucent text over that ground
before measuring. `DESIGN_PRINCIPLES.md` §8 records that three sweeps lied by skipping one of
those; the function was copied rather than rewritten so it could not lie a fourth way.

**Type is measured on the same leaf set as contrast** — an element with no element children,
non-empty trimmed text, a box at least 2×2, not `hidden`/`opacity:0`/`display:none` — so the
ratios below are comparable to the 2.97× the tier's own note quotes.

**"Mid-word" is computed, not eyeballed.** For every leaf with `text-overflow: ellipsis` that
is actually overflowing, a `Range` walks the text character by character to find the first one
clipped by the content box, and reports whether the characters either side of that cut are both
word characters. `IDEN… 8` is what §3 forbids; a cut at a space is not.

**A readiness gate runs before every measurement.** `Shell.tsx:738` —
`if (!org && tableCount === 0) return <Onboarding />` — means a reload measured before
IndexedDB rehydrates measures the **onboarding screen** and calls it whatever stage it asked
for. That happened once and produced a 12-leaf "module workspace". Every navigation now waits
for `nav.sn` + `main.shell-stage` with no `.ob-stage` present.

Screenshots (both widths, twelve screens each) are in the session scratchpad, not the tree —
`*.png` is gitignored and `.gitignore:28-29` says agent screenshots belong there. The numbers
below are the evidence; the pictures are not.

## 2 · WHAT IS STILL WRONG — TEN FINDINGS, RANKED, WORST FIRST

### 1 · The display tier reached one screen out of ten, and the home stage went backwards

`src/features/dashboard/dashboard.css:2981`

The tier exists and it works — 82.86px on the configurator, exactly the contract's number. It
just is not anywhere else. Eleven of the twelve rows above sit between **2.44× and 3.96×** at
1280 and between **2.36× and 3.17×** at 1024, and `PHASE_TWO` §3 asks for about **7×**.

The home stage is the sharp case, because it is where the 2.97× that justified the whole tier
was measured. `dashboard.css:231-260` deliberately took the 32.7px greeting down to a caption
and moved the display step to the four doors — a correct diagnosis. But `.dsh-door-name` takes
`--t-display-lg`, which resolves to **26.88px** at 1280, so the screen's largest glyph got
*smaller* than the greeting it replaced:

```
before the tier   32.7px greeting     ÷ 11px  =  2.97×
after the tier    26.88px door name   ÷ 11px  =  2.44×   ← measured today
```

`dashboard.css:2942-2981` argues carefully that the marque is wrong for a door and hero is
wrong for four of them, and both arguments hold. The consequence nobody wrote down is that the
door is then capped at a step **five pixels below** what the screen already had.

Home only reaches 3.04× when a draft exists, because the one `--t-figure-xl` on the screen is
`.dsh-worth-n` (`dashboard.css:2699`) and it is not drawn on an empty book. **A dealer's first
afternoon is measured at 2.44×.**

### 8 · The marque's documented floor is unreachable, and 7.53× is a ≥1280 number

`docs/specs/DESIGN_CONTRACT.md:171` · `src/features/quote/build.css:649`

The contract's table row reads *"→ 72px @1024"*. Measured at 1024: **34.82px**.

Both statements in the contract are individually true and they contradict each other. The clamp
does bottom at 72px. But the identity column at 1024 is **313px** wide (`.qb-name` 272px), and
`build.css:649` `@container (max-width: 340px)` takes the whole `--t-hero` set instead —
34.82px / 680 / 1.03 / `wdth` 105. The prose four paragraphs down says exactly that. The table
row, which is what a reader copies, says 72px.

Measured host widths: **401px at 1280** (marque, 82.86px) → **313px at 1024** (hero, 34.82px).
The marque never renders at its own floor through the only surface that wears it, so **72px is
a number in a document and not a size the app can draw.** Either the row carries the swap or it
should say 82.9px is the smallest a marque is ever seen at.

The consequence for finding 1's headline: the app's one 7× screen is 7× **only at 1280 and above**. At
1024 the configurator is 3.17×, the same as customers and the module workspace.
